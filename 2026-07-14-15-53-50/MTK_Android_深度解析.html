MTK Android 深度解析

从 preloader → LK → ATF → Kernel → Framework → HAL 的 AOSP 代码级拆解，并对比高通平台 · 适用于 MT67xx / MT68xx (Dimensity) / Android 11–14

说明：MTK 代码分两类 —— ① AOSP 直接 patch（在 frameworks/base 等上游目录里改）；② 独立仓库（在 vendor/mediatek/proprietary/ 下）。文中路径以常见 MT68xx + Android 12/13 布局为准，不同芯片/版本会有差异。

0. 总览：MTK 软件栈分层

MTK 在 AOSP 之上叠加了大量「Mtk」前缀的系统服务与 HAL，并把 modem（MD）作为独立核通过 CCCI 与 AP 通信。整体栈如下：

1. Boot / 内核 / 驱动

1.1 启动链全景

上电后依次经过 preloader → LK →（加载 TEE/ATF）→ 内核 → init → zygote → system_server。流程图：

1.2 preloader（源码在 vendor 仓库）

路径：vendor/mediatek/proprietary/bootable/bootloader/preloader/

# 平台相关初始化入口（以 MT6983 为例）
platform/{chip}/src/{chip}.c        → platform_init(), platform_early_init()
platform/{chip}/src/uart.c          → 早期串口
platform/{chip}/src/emi.c          → DRAM 初始化（最关键，写满 timing 表）
platform/{chip}/src/pmic.c         → PMIC 上电时序
# 主流程
main() → platform_early_init() → platform_init() →
boot_linux_from_storage()  // 把 LK 从 storage 读到 DRAM 并跳转
preloader 运行在片内 SRAM（容量极小，~百 KB），只做「能跑起 LK」的最小初始化；DRAM 没起来之前连 C 运行时栈都受限，所以代码高度汇编/手写。

1.3 LK（Little Kernel）

路径：vendor/mediatek/proprietary/bootable/bootloader/lk/。关键应用与流程：

app/mt_boot/mt_boot.c      → mt_boot_init() 注册 aboot 命令
app/mt_boot/bootimg.c      → 解析 Android boot image (vendor_boot + boot)
app/mt_boot/mt_boot.c:
  boot_linux_from_storage()  // 读 boot/vendor_boot 分区
  boot_linux()              // 准备 DTB、cmdline，最终 entry() 跳内核
app/meta/                  → 工厂 Meta 模式入口（adb reboot meta 进此分支）
app/charger/              → 关机充电
platform/{chip}/           → 平台早期外设、LCM(屏) 初始化、显示 logo

LK 通过 libptgen 读取分区表（来自 partition_table / pgpt 镜像），按名取分区偏移，再把内核/ramdisk/dtbo 载入内存。

1.4 TEE / ATF（ARMv8 安全启动）

路径：vendor/mediatek/proprietary/trustzone/ 与 ATF（trusted-firmware-a 的 MTK 分支）。preloader 把 TEE + ATF 镜像载入，先跳 ATF(EL3) 建立安全世界，再返回 LK(EL1)。MTK 既支持 Google Trusty，也有自研 TEE；keypair / drm / 指纹等安全 TA 跑在 EL3/SEL0。

1.5 Linux 内核里的 MTK 痕迹

MTK 几乎把所有 SoC 驱动放进 drivers/misc/mediatek/ 与 drivers/soc/mediatek/，而不是像上游那样分散。常用子系统：

子系统路径作用
EINTdrivers/misc/mediatek/eint/外部中断控制器（按键/TP 唤醒）
PMICdrivers/misc/mediatek/pmic/电源管理 IC 寄存器中继
SCPdrivers/misc/mediatek/scp/Sensor Control Processor（协处理器，跑传感器算法）
CCCIdrivers/misc/mediatek/ccci/AP ↔ MD(modem) 跨核通信（见 §3.4）
CMDQ / M4Udrivers/misc/mediatek/cmdq/ · m4u/显示命令队列 / IOMMU
DRM 显示drivers/gpu/drm/mediatek/DRM/KMS 显示管线（替代旧 fbdev）
Vcodecdrivers/media/platform/mediatek/视频编解码硬件（VDEC / VENC）

设备树：arch/arm64/boot/dts/mediatek/（如 mt6983.dts / mt6878.dts），与 QCOM 的 arch/arm64/boot/dts/qcom/ 同属一脉但节点命名完全不同。

2. Framework 层定制（MTK 的核心差异点）

MTK 不像高通那样「尽量用原生 + 独立 HIDL」，而是大量直接 patch AOSP 的 Java 框架，并用 Mtk 前缀类做扩展。两个来源：

① AOSP 直接 patch

在 frameworks/base/ 里改原文件，例如 ActivityManagerService、PowerManagerService、PhoneWindowManager 被就地插入 MTK 逻辑（双卡、游戏模式、分屏增强等）。

② 独立 proprietary 仓库

vendor/mediatek/proprietary/frameworks/ 下新建 Mtk* 类与服务，由 MtkSystemServer 统一拉起。

2.1 系统服务如何被拉起

# 入口被 patch 过：frameworks/base/services/java/com/android/server/SystemServer.java
run() → startBootstrapServices() / startCoreServices() / startOtherServices()

         startMtkBootstrapServices()
         startMtkCoreServices()        // e.g. MtkTelephonyRegistry
         startMtkOtherServices()       // e.g. MtkBatteryService, PerfService

2.2 AEE —— MTK 的「崩溃总管」

路径：vendor/mediatek/proprietary/external/aee/ + 内核侧 kernel-*/drivers/misc/mediatek/aee/。

# 关键组件
libaed        → 异常捕获库（native/kernel 崩溃时写 db）
aed           → /system/bin/aed 守护进程，收集 kernel/modem/native exception
expdb 分区    → 异常数据库持久化
/data/aee_exp/  → 落盘的 db 文件（手机关机重启前可抓）

当发生 KE（Kernel Exception）、NE（Native Exception）、JE（Java Exception）、EE（Modem Exception） 时，AEE 会触发 reboot 并把现场存进 /data/aee_exp/。调试时这是第一手材料 —— 比单纯 logcat 强太多。

2.3 PerfService —— 性能调度接口

路径：vendor/mediatek/proprietary/frameworks/base/perfservice/。App 通过 PerfServiceWrapper 申请「锁频/锁核」，典型用于游戏与相机预览防卡顿：

android.util.PerfServiceWrapper
  perfLockAcquire(int duration, int[] resource)  // 拉满 CPU/GPU 频率
  perfLockRelease()

2.4 通信/电话（MTK 重灾区）

MTK 双卡双待 historically 大量 patch 了 telephony 栈：

vendor/mediatek/proprietary/frameworks/opt/telephony/   → MtkGsmCdmaPhone, MtkRIL
packages/services/Telephony/                            → MtkPhone / 双卡 UI
frameworks/opt/telephony/                               → 被 Mtk 补丁注入多卡逻辑

3. HAL / vendor 架构

3.1 目录结构

几乎所有 MTK HAL 都在 vendor/mediatek/proprietary/hardware/ 与 vendor/mediatek/proprietary/libs/：

模块路径说明
Cameravendor/mediatek/proprietary/hardware/mtkcam/相机 HAL（Pipeline + 3A + ISP 配置），非常庞大
Audiovendor/mediatek/proprietary/hardware/audio/音频 HAL（Speaker/Headset/VOIP）
Displayvendor/mediatek/proprietary/hardware/hwcomposer/ · gralloc/HWC / 图形内存分配
Videovendor/mediatek/proprietary/hardware/vcodec/硬编硬解
GPSvendor/mediatek/proprietary/hardware/gps/定位 HAL
Sensorvendor/mediatek/proprietary/hardware/sensor/传感器 HAL（接 SCP）

接口形态：Android 8–11 主要用 HIDL（vendor.mediatek.hardware.*），Android 12+ 逐步迁移到 AIDL。与高通的 vendor.qti.hardware.* 命名空间不同。

3.2 NVRAM —— MTK 的「参数保险箱」

路径：vendor/mediatek/proprietary/external/nvram/。存 IMEI、RF 校准、网络参数等，落盘在 nvram 分区，由 nvram_daemon 管理。刷机/写号工具（SN Writer、Meta）本质上就是在改这里。

3.3 Meta 模式

vendor/mediatek/proprietary/external/meta/ + meta_daemon。工厂校准/写号/RF 测试专用模式，adb reboot meta 或组合键进入，与普通 recovery / fastboot 完全独立。

3.4 CCCI —— AP 与 Modem 的「桥梁」

内核：kernel-*/drivers/misc/mediatek/ccci/；用户态：vendor/mediatek/proprietary/hardware/ccci/。MTK 把 modem（MD）做成独立核（常跑 Nucleus/ThreadX），AP 通过 CCCI 字符设备 + 共享内存与其通信（AT 命令、数据传输、异常上报）。这是 MTK 与高通「外挂/集成 modem」路线差异的核心（见 §4）。

5. 调试与抓 log 的 MTK 特色

mtklog（Mobile Log）

路径：vendor/mediatek/proprietary/external/mtklog/。工程版可通过 *#*#3646633#*#* 进入 EngineerMode 开启 mtklog，分多路：

mobilelog/   → logcat + kernel log
modemlog/    → MD 侧 AT/协议栈日志（CCCI 抓取）
metaplog/    → AEE / aed 异常日志
netlog/      → 网络层

AEE / aed 抓死机

死机重启后第一时间去 /data/aee_exp/ 取 db.*.zip；内核 panic 还能配合 ram_console / pstore 看 last_kmsg。
