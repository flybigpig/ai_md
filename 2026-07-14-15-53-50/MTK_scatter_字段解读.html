MT6893 scatter 文件字段逐项解读

以 MT6893_Android_scatter.txt 为例 · 回应「scatter 不匹配就变砖」的硬约束 · 原文框架由 WorkBuddy 编写
平台 mt6893Android 14EMMC动态分区
核心认知：scatter 就是 SP Flash Tool 的"分区地图"。每个分区的 linear_start_addr 和 partition_size 一旦和镜像实际布局对不上，烧录要么直接报错，要么把邻区覆盖成砖。

一、文件头部（General Setting）

SP Flash Tool 先读这段，确认平台/存储匹配，不匹配会直接拒绝加载：

- general: MTK_PLATFORM_CFG
  INFO:
    - config_version: V1.1.2
    - platform: MT6893
    - project: mt6893
    - storage: EMMC
    - boot_channel: MSDC_0
    - kernel: linux
    - wifi:
    ...
字段含义注意
config_versionscatter 格式版本V1.x 为 MTK 私有格式；换大版本工具可能不认
platform: MT6893芯片平台必须和你要烧的机器一致，写错直接拒
storage: EMMC存储介质也有 UFS（UFS）；混用必 brick
boot_channel: MSDC_0启动通道eMMC 走 MSDC 控制器，一般不动

二、分区条目字段逐项解读

每个分区是一个 - partition_index: 块。下面用 MT6893 上一个真实形态的分区做样例（数值为示意，以你 BSP 实际为准）：

- partition_index: SYS0
  partition_name: preloader
  file_name: preloader_mt6893.bin
  is_download: true
  type: SV5_BL_BIN
  linear_start_addr: 0x0
  physical_start_addr: 0x0
  partition_size: 0x80000
  region: EMMC_BOOT_1
  storage: HW_STORAGE_EMMC
  boundary_check: true
  is_reserved: false
  operation_type: BOOTLOADERS
  d_type: FALSE
  reserved: 0x00

- partition_index: SYS1
  partition_name: recovery
  file_name: recovery.img
  is_download: true
  type: NORMAL_ROM
  linear_start_addr: 0x400000
  physical_start_addr: 0x400000
  partition_size: 0x2000000
  region: EMMC_USER
  storage: HW_STORAGE_EMMC
  boundary_check: true
  is_reserved: false
  operation_type: UPDATE
  d_type: FALSE
  reserved: 0x00

- partition_index: SYSx
  partition_name: super
  file_name: super.img
  is_download: true
  type: SUPER_IMG
  linear_start_addr: 0x....
  partition_size: 0x.....
  region: EMMC_USER
  storage: HW_STORAGE_EMMC
  boundary_check: true
  operation_type: UPDATE
  d_type: FALSE
  reserved: 0x00
字段含义Android 14 / MT6893 注意点
partition_index条目序号 SYS0..SYSn必须连续，工具按序处理；乱序可能导致布局解析错
partition_name分区名与 fstab、avb 对应；如 preloader recovery super vbmeta
file_name要烧的镜像文件名相对 out/target/product/mt6893/；留空则只擦除不烧
is_download是否烧录false 工具跳过；动态分区的 system/vendor/product 常设为 false（在 super 内）
type镜像类型SV5_BL_BIN(preloader) / NORMAL_ROM / EXT4_IMG / SUPER_IMG / FB_IMG(fastboot) 等；类型错工具拒烧
linear_start_addr逻辑起始地址★ 错配→覆盖邻区变砖；必须用本次编译生成的值
physical_start_addr物理起始地址EMMC 上一般等于 linear；BOOT_1/BOOT_2 区域不同
partition_size分区大小（hex）★ 必须 ≥ img 实际大小；不足则烧录截断/失败
region存储区域EMMC_BOOT_1 / EMMC_BOOT_2 / EMMC_USER；preloader 在 BOOT_1
storage存储介质HW_STORAGE_EMMC（或 UFS）
boundary_check边界检查true 时工具校验不越界；关掉等于自找砖
operation_type操作类型BOOTLOADERS(preloader/lk) / UPDATE / PROTECTED(protect1/2)
d_type是否数据分区TRUE=裸数据分区（如 userdata）；FALSE=镜像
reserved保留字节一般 0x00，勿改

三、为什么"不匹配就变砖"

三个致命点：
  1. linear_start_addr 重叠：A 分区的起始落进了 B 分区的区间，烧 A 直接把 B 覆盖。典型是手改了某个地址却没同步相邻分区。
  2. partition_size < img 实际大小：镜像写不下，工具报错或静默截断，开机即挂。
  3. region 错挂：把本该在 EMMC_USER 的镜像指到 EMMC_BOOT_1，preloader 区被冲，连 BROM 都救不回（需外部强刷）。
结论：永远用本次编译生成的 scatter，不要拿别的机型/版本的 scatter 来烧 MT6893；跨 Android 大版本（11→14）分区表几乎必然变（多了 vendor_boot、super、多张 vbmeta），更不能混用。

四、Android 14 动态分区在 scatter 里的体现

动态分区下，system / vendor / product / system_ext / odm 不再是独立物理分区，而是 super 内部的逻辑分区。scatter 里通常表现为：

  • 有一个大 super 分区（type: SUPER_IMG），is_download: true；
  • system/vendor/product 等条目要么不出现，要么 is_download: false，仅作占位；
  • 烧录时只勾 super.img，不要单独烧 system/vendor。
# 动态分区场景：system 在 super 内，scatter 里一般这样
- partition_index: SYSn
  partition_name: system
  file_name:
  is_download: false        # ★ 不单独烧
  type: EXT4_IMG
  ...

- partition_index: SYSm
  partition_name: super
  file_name: super.img
  is_download: true         # ★ 只烧这个
  type: SUPER_IMG
  ...

五、与 SP Flash Tool 的对应关系

graph TD SC["scatter.txt
(分区地图)"] --> PF["SP Flash Tool 读取"] PF --> CHK["校验 platform/storage 匹配"] CHK --> LIST["列出分区 + is_download 过滤"] LIST --> DL["按 linear_start_addr 顺序烧录"] DL --> BR["boundary_check 防越界"] BR --> OK["绿色 ✓ Download OK"]
排障速记：
  • BROM ERROR: STATUS_SEC_IMG_NOT_FOUND → 没加载 auth 文件（Secure Boot）。
  • linear_start_addr 报错 → scatter 与镜像版本不符，换本次编译的。
  • 烧完不开机但能进 BROM → 多半是 boot/vendor_boot/dtbo 没同烧（GKI 分离坑）。
