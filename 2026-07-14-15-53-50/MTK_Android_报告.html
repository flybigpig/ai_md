MTK Android 深度解析（用户编写版）

按 AOSP 代码级 + 真实路径/类名 + 图示 组织 · 含 MTK vs 高通维度对比 · 已渲染 mermaid 图示

本文由用户撰写，按「AOSP 代码级 + 真实路径/类名 + 图示」要求组织。MTK 专有代码（vendor/mediatek/proprietary/）为闭源 BSP，公开路径来自 partner 发布包与社区逆向整理，不同芯片（MT67xx / MT68xx / Dimensity）与 Android 版本（11/12/13/14）目录名会有差异，关键处已标注。

一、整体架构概览

MTK（MediaTek）Android 平台 = 标准 AOSP + MTK 私有 BSP 叠加层。MTK 的定制集中在 vendor/mediatek/proprietary/，对 frameworks/base、system/ 的修改通过 device/mediatek/ 下的 overlay 与 patch 注入。

核心思路：越往下 MTK 私有比例越高，越往上越接近原生 AOSP。Treble 之后，/vendor 与 /system 分离，MTK 的 HAL 全部落在 vendor 分区。

二、启动链（Boot Chain）

MTK 与高通最大的区别就在这一层：MTK 用 preloader + LK（Little Kernel），没有 UEFI；高通新平台用 XBL（UEFI）+ ABL。

三、Framework 定制

MTK 对 Framework 的修改遵循两条线：(1) 在 frameworks/base 里以 com.mediatek 包名打补丁；(2) 在 vendor/mediatek/proprietary/frameworks/ 放独立模块。

  • frameworks/base/core/java/com/mediatek/server/MtkSystemService.java — MTK 服务注册入口（被 SystemServer 的 MTK patch 调用）。
  • frameworks/base/services/core/java/com/mediatek/server/telephony/MtkTelephonyRegistry.java — 电话状态广播扩展（双卡、IMS）。
  • frameworks/base/policy/src/com/mediatek/policy/MtkPhoneWindowManager.java — 在原生 PhoneWindowManager 之上叠加 Smart Cover、手势唤醒、翻转静音等。
  • frameworks/opt/telephony/src/java/com/mediatek/internal/telephony/MtkRIL.java — 继承 RIL，扩展 MTK 私有 RIL 请求（RIL_REQUEST_* 的 MTK 区间）。

3.2 AEE（Application Exception Engine）

MTK 的"崩溃收集/重启"体系，相当于 MTK 版的 debuggerd + tombstoned 增强：

  • vendor/mediatek/proprietary/frameworks/aee/ → libaee.so、libaed.so
  • aee_common.h 定义异常类型（AE_EXP_*：KE / HW / NE / JE / SWT）
  • 内核侧 kernel-*/drivers/misc/mediatek/aee/ 提供 aee_kernel_api
  • mtklogger（vendor/mediatek/proprietary/packages/apps/MTKLogger/）负责把 exp_* 目录打包

3.3 配置 / Overlay

  • device/mediatek/mt68xx/：device.mk、manifest.xml（vintf）、overlay/
  • vendor/mediatek/proprietary/frameworks/base/res/：MTK 资源 overlay
  • MtkSettings 替换原生 Settings（packages/apps/MtkSettings/）

启动链对比图

graph LR subgraph MTK["MTK"] M1[Preloader] --> M2[LK] M2 --> M3[ATF/Trustonic] M3 --> M4[Kernel] end subgraph QC["Qualcomm"] Q1[PBL] --> Q2[XBL + TZ(UEFI)] Q2 --> Q3[ABL] Q3 --> Q4[Kernel] end
核心差异总结：
  1. Bootloader 范式：MTK 是 "轻量 C bootloader + LK"，QC 是 "UEFI（XBL）+ ABL"。UEFI 更重但更标准化。
  2. 安全 OS：MTK 用第三方 Trustonic；QC 自研 QTEE，生态更封闭但和 Snapdragon 特性耦合更深。
  3. 图形/相机管线：两者都自研且闭源，但 MTK 的 mtkcam 与 QC 的 CAMX-CHI 架构完全不同，移植一套算法到另一平台几乎要重写。
  4. 开源程度：QC 在 CodeLinaro 上放出更多 opensource/ 组件，MTK 的公开资料相对少，调试更依赖 partner 文档与 aee 日志。

六、版本 / 芯片差异提示

  • MT67xx（Helio G/P 系列，Android 9–12）：LK 时期，HAL 多为 HIDL 旧式。
  • MT68xx / Dimensity（Android 12+）：kernel-5.15/6.1，引入 mcupm、spm 新固件，HAL 切 AIDL 比例增大。
  • Treble 前后：Android 8 之前 MTK HAL 直接 dlopen 进 system；之后强制 vendor 分区 + vintf manifest。
〔补充·助理注，不改原文〕路径差异与 TEE 注记
  • LK / preloader 路径双树问题：你文中用的是 bootable/bootloader/lk/ 与 bootloader/preloader/（即 AOSP 侧 / 发布包顶层相对路径）；我前一份报告写的是 vendor/mediatek/proprietary/bootable/bootloader/lk/（私有仓绝对前缀）。两者指向同一份代码，只是"树根"不同——partner drop 常把 bootable/ 等作为顶层目录释放，而整树合入 AOSP 后挂在 vendor/mediatek/proprietary/ 下。阅读时以你手头代码树的 root 为准。
  • TEE 不止 Trustonic：Kinibi（Trustonic）确实是 MTK 主流 TEE，但部分平台/版本也采用 Google Trusty，或 MTK 自研 TEE。报告里写"Trustonic Kinibi"作为代表是准确的，仅提醒存在变体。
  • AEE 与原生组件关系：你的描述（MTK 版 debuggerd + tombstoned 增强）贴切。补充一点：在 Android 8+ 原生已有 tombstoned 与 debuggerd，AEE 是在其之外另起一套 aed 守护 + 内核 aee_kernel_api，二者并存，AEE 负责跨 AP/MD 的"整机级"异常聚合。
  • MTKLogger 路径：你写 vendor/mediatek/proprietary/packages/apps/MTKLogger/，与社区 drop 一致；部分版本包名是 com.mediatek.mtklogger。
