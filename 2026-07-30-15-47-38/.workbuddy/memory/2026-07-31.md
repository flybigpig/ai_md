## 交付：dumpsys 超时机制 + 车载 SurfaceFlinger TIMEOUT 根因分析

文件：`dumpsys-timeout-surfaceflinger-android14.md`（工作区根目录）
基线 Android 14 (UpsideDownCake)。承接 7-30 的 frameworks/native/cmds 版本校正。

### 核心技术结论（可复用）
- dumpsys 超时是**总预算**语义：`writeDump()` 里 `end = start + timeout` 循环外算一次，
  每轮 poll 用剩余量。数据一直流出但总耗时超 10s 同样 TIMED_OUT。
- 默认 10000ms；`-t` 单位秒，`-T` 单位毫秒，`-T 0` = 无限等（排障最有用）。
- 机制三件套：`startDumpThread()` pipe+std::thread 发 binder → `writeDump()` 主线程
  poll/read 计时 → `stopDumpThread()` 完成 join / 超时 detach。
- **超时 ≠ 取消**：binder 不支持取消 in-flight 同步事务，SF 侧继续跑。
  dumpstate 静态链 libdumpsys，多次超时会累积 detached 线程。
- `main.cpp` 的 `signal(SIGPIPE, SIG_IGN)` 是关读端后写端拿 EPIPE 而非被杀的前提。

### SF 三个阻塞点
- A（最危险，无超时）：`mScheduler->schedule([&]{traverseInZOrder}).get()` —— SF 主线程一卡就死等
- B（有 1s 超时，优雅降级）：`SurfaceFlinger.h::struct TimedLock(mStateLock, s2ns(1))`
- C（不可控）：`HWComposer::dump()` → `AidlComposerHal::dumpDebugInfo()` 跨进程调 vendor composer3

### bugreport 比命令行更易超时的原因
`main_surfaceflinger.cpp` 注册时带 `DUMP_FLAG_PRIORITY_CRITICAL`，
dumpstate 的 `RunDumpsysCritical()` per-service 超时是秒级/亚秒级，远小于 CLI 的 10s。

### 车载放大因素（按命中率）
多屏高 layer 数(纯慢) > 串行器/fence 不返回(死) > vendor composer dump 卡 >
SF binder 线程池打满(没进 dump) > EVS 抢 display > winscope trace 开着

### 排障要点
- 分段 dump 二分定位：`--list` / `--display-id` / `--vsync` / `--timestats` / `--latency`
- SF 是 native 进程，抓栈用 `debuggerd -b $(pidof surfaceflinger)`，不是 kill -3
- binder 日志在 `/dev/binderfs/binder_logs/`（Android 11+），不是 debugfs
- patch `schedule().get()` 加超时时，必须把 `[&]` 改成 shared_ptr 值捕获，否则 UAF

### 待办 / 后续可展开
用户仍未选的方向：OomAdjuster 14 版链路、BroadcastQueueModernImpl、
ProcessList 启动链路、CachedAppOptimizer 冻结 + binder_freeze、
新增 AIDL HAL 全链路（VINTF 声明 → init.rc → selinux → isDeclared）
